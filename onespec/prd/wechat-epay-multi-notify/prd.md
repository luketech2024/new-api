# 微信支付适配器多业务回调需求文档

## 0. 评审摘要（必读，约 2 页）

> 本节供产品、研发、测试快速评审；详细条款见 `## 1` 及之后。
> 本需求来自已落地实现的回顾整理，无禅道 Story ID。它修正变更 #45 首期「只验收钱包充值」带来的运行时限制。

### 0.1 一句话需求

让同一套微信支付适配器同时服务 new-api 的钱包充值和订阅购买：进单时允许两条合法回调地址，支付成功后把结果送到该订单自己登记的回调路径，而不是全局只投一个地址。

### 0.2 做什么 / 不做什么

- **做什么**：适配器侧把「new-api 异步通知地址」从单一精确值改为逗号分隔允许列表；进单校验与支付成功投递都按订单自己的通知地址执行；单个旧配置值仍能启动。
- **不做什么**：不改 new-api 后台「回调地址」字段语义（仍只填站点根域名）；不合并钱包与订阅两个回调接口；不改微信 Native 下单、收银台、验签解密、订单状态机和人工补偿主流程；不接入其他支付渠道。

### 0.3 关键流程或生效方式

1. 运维在适配器环境中列出钱包充值和订阅购买两条完整通知地址（环境变量名保持不变）。
2. 用户在 new-api 发起微信支付：钱包充值走自己的通知路径，订阅购买走自己的通知路径。
3. 适配器只接受允许列表内的通知地址，并把规范化后的地址随订单保存。
4. 微信支付成功后，适配器向**该订单保存的通知地址**发送易支付成功回调。
5. new-api 各业务接口只结算自己的订单表，互不串单。

### 0.4 验收怎么测

- 允许列表同时包含两条地址时，钱包充值和订阅购买都能进单、扫码、到账。
- 只配其中一条时，未列出的那条流程在进单阶段被拒绝，已列出的仍可用。
- 支付成功后，钱包回调不得落到订阅接口，订阅回调不得落到钱包接口。
- 后台「回调地址」继续只填根域名，不要求改成带路径的完整 URL。
- 旧配置只写一条完整通知地址时，适配器仍能启动，行为与改前一致。

## 2. 项目概述

### 2.1 项目背景

变更 #45 建设了微信支付适配器，并以钱包充值为验收主场景。适配器把 new-api 通知地址做成**全局唯一精确匹配**：进单必须等于该地址，成功后也只向该地址投递。

new-api 本身为钱包充值和订阅购买分别登记了不同的异步回调路径。后台「回调地址」只填根域名，两条路径由后端拼接。因此只要把适配器接到这两类业务，就必然出现「只能保一边」：配钱包地址则订阅进单被拒；配订阅地址则钱包进单被拒；即便进单被放行，成功回调也会投到错误业务接口。

### 2.2 项目目标

1. 同一适配器实例可同时处理钱包充值和订阅购买的微信支付。
2. 支付成功后的异步通知必须到达该订单所属业务的回调路径。
3. 未列入允许列表的通知地址仍被拒绝，不得弱化为「同域任意路径都放行」。
4. 已上线的单地址配置可平滑升级：只配一条时行为与改前一致。

### 2.3 用户角色

| 角色 | 诉求 |
|------|------|
| 终端用户 | 钱包充值和购买套餐都能用微信支付，付完后各自到账 |
| 站点管理员 | new-api 后台支付配置无需为两条业务各填一套根域名 |
| 运维 | 在适配器环境变量中显式列出允许回调的完整地址并重启生效 |

## 3. 功能需求

### 3.1 允许列表配置

**优先级**：P0

**需求描述**：
作为运维，我想在适配器上配置一条或多条 new-api 通知地址，以便钱包和订阅可以同时接微信支付。

**操作流程**：
1. 运维在适配器环境中填写通知地址配置（名称与既有配置键一致）。
2. 需要同时开通两条业务时，用逗号列出两条完整 HTTPS 地址。
3. 仅开通一条业务时，仍可只填一条完整地址。
4. 重启适配器后新配置生效。

**验收标准**：
1. 当配置包含钱包通知地址和订阅通知地址时，支付适配器应成功启动。
2. 当配置只包含一条合法完整通知地址时，支付适配器应成功启动，且仅该地址可被进单使用。
3. 当配置为空、含非 HTTPS 或含无法解析的项时，支付适配器应拒绝启动。
4. new-api 后台「回调地址」应继续只填写站点根域名；运维不应被要求把带路径的业务回调写进该后台字段。

**业务属性**：

| 属性名 | 业务类型 | 业务约束 | 说明 | 示例 |
|--------|----------|----------|------|------|
| 通知地址允许列表 | 文本，逗号分隔 | 至少一条；每条均为完整 HTTPS 地址 | 环境变量名保持既有键名 | 钱包路径,订阅路径 |
| 后台回调地址 | 站点 origin | 不含业务路径 | 由 new-api 拼接具体路径 | `https://token-api-test.example.com` |

### 3.2 进单接受多业务通知地址

**优先级**：P0

**需求描述**：
作为终端用户，我想钱包充值和订阅购买都能提交到同一微信支付适配器，以便不必因回调路径不同而失败。

**操作流程**：
1. 用户在 new-api 选择微信支付并发起钱包充值或订阅购买。
2. new-api 按各自业务拼接通知地址并提交易支付表单。
3. 适配器校验签名、金额，并确认通知地址落在允许列表内。
4. 适配器保存该订单使用的通知地址，再走既有微信 Native 下单与收银台。

**验收标准**：
1. 当允许列表同时包含两条业务通知地址，且请求签名、金额合法时，支付适配器应为钱包充值和订阅购买分别创建订单。
2. 当请求中的通知地址不在允许列表内时，支付适配器应拒绝创建订单。
3. 当同一商户订单号再次提交且关键字段（含通知地址）一致时，支付适配器应返回原订单结果，不得新建重复订单。
4. 当同一商户订单号再次提交但通知地址与原订单不同时，支付适配器应拒绝冲突请求并保留原订单。

### 3.3 按订单投递成功回调

**优先级**：P0

**需求描述**：
作为站点，我希望支付成功后的异步通知落到正确业务，以便钱包加额和订阅开通互不干扰。

**操作流程**：
1. 用户完成微信扫码支付。
2. 适配器按既有规则验签、核对金额并确认支付。
3. 适配器读取该订单保存的通知地址。
4. 仅当该地址仍在当前允许列表内时，向该地址发送易支付成功回调。
5. new-api 对应接口完成钱包充值或订阅开通。

**验收标准**：
1. 当钱包充值订单支付成功时，支付适配器应向该订单的钱包通知地址发送成功回调，且不得改投订阅通知地址。
2. 当订阅购买订单支付成功时，支付适配器应向该订单的订阅通知地址发送成功回调，且不得改投钱包通知地址。
3. 当订单保存的通知地址已不在当前允许列表内时，支付适配器应停止向该地址投递，记录失败并按既有重试策略处理，不得改投列表中的其他地址。
4. 当回调发生重定向时，支付适配器应再次校验目标仍属于允许列表。
5. 浏览器同步返回不得作为到账依据；到账仍以服务端异步通知为准。

## 4. 异常与边界

- 若运维只配置了钱包通知地址，当用户发起订阅微信支付时，支付适配器应拒绝进单。
- 若运维只配置了订阅通知地址，当用户发起钱包微信支付时，支付适配器应拒绝进单。
- 若跳转地址未覆盖订阅同步返回路径，当用户完成订阅支付后，支付适配器应拒绝不可信跳转；运维应把同步返回允许范围配到能覆盖两条业务回跳。
- 若升级前已存在待投递任务，支付适配器应使用订单上已保存的通知地址继续投递，不得要求改写历史任务内容。
- 本需求不改变微信通知验签、金额核对、幂等到账和人工审查规则。

## 5. 界面变更

- new-api 管理后台支付设置无需改文案语义：回调地址仍提示「只填站点根域名，不要填写业务路径」。
- 适配器环境示例与部署说明应写明：同时开通两条业务时，通知地址配置需逗号列出两条完整路径。

## 6. 影响范围

- 模块：`wechat-epay-adapter`（配置加载、进单校验、通知投递、SSRF 目标校验）
- 配置：适配器环境变量 `NEW_API_NOTIFY_URL` 取值从单地址扩展为允许列表；`RETURN_URL_ALLOWLIST` 需覆盖订阅同步返回
- 非范围：new-api 钱包/订阅回调处理逻辑、易支付商户号与密钥、微信商户材料

## 7. 范围外

- 将钱包与订阅合并为单一回调入口或按订单号前缀在 new-api 内部分流
- 修改 new-api 后台「回调地址」为完整路径
- 支付宝及其他渠道、微信 JSAPI/H5/小程序
- 自动退款、分账、多商户
- 运行时热更新允许列表（仍为启动加载）
