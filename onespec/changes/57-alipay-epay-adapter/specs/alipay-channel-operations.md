# Delta Spec: 双渠道隔离、运维补偿与密钥安全

> 本文件聚焦支付宝与微信共用同一适配器时的隔离、可运营性和密钥保护，是对 `../proposal.md §2.4 渠道隔离、运维与密钥安全` 的精化。
> 进单分流见 `epay-alipay-intake.md`；通知核对与到账见 `alipay-settlement.md`。

## 1. 需求描述 (中文 EARS)

**主流程**:
- 当订单创建时选定支付类型后，wechat-epay-adapter 应在后续出码、验通知和回写易支付类型时沿用该类型，不得中途改渠道。
- 当授权管理员按商户订单号查询时，wechat-epay-adapter 应返回支付渠道、外部交易号、金额、支付时间、通知状态、重试次数和最近失败原因，且渠道与下单类型一致。
- 当授权管理员对已支付但通知未成功的订单执行人工重试时，wechat-epay-adapter 应复用原通知任务，记录操作者与结果，不得创建新的支付订单。

**前置约束**:
- 若支付宝必要配置不完整，wechat-epay-adapter 应拒绝新的支付宝下单，且不得使用微信密钥材料冒充支付宝验签或下单。
- 若微信必要配置完整，即使支付宝不可用，wechat-epay-adapter 仍应允许合法微信下单。
- 若请求未通过认证授权，wechat-epay-adapter 应拒绝订单详情查询和人工重试。
- 支付宝应用私钥、支付宝公钥与微信商户密钥应分开注入；不得写入镜像、数据库或代码仓库。

**异常与边界**:
- 在数据库不可用的情况下，就绪检查应返回不可接流量状态。
- 当支付宝通知积压、连续回调失败或订单进入人工审查时，wechat-epay-adapter 应产生可按渠道观察的指标并触发已配置告警。
- 日志应包含可关联的订单号、渠道和请求标识，不得输出完整密钥、私钥、签名原文或可复用支付凭据。
- 支付宝公钥或证书轮换时，wechat-epay-adapter 应支持按标识选择新旧材料并完成安全过渡。
- 回滚支付宝能力时，wechat-epay-adapter 应仍能查询已存在的支付宝订单并补偿未完成通知，不得删除已确认到账结果。

## 2. 验收标准

- [ ] **渠道锁定**: 给定支付宝订单，当完成出码、通知和回调后，全程支付类型保持为支付宝。
- [ ] **微信不受支付宝配置影响**: 给定支付宝配置缺失、微信配置完整，当提交合法微信订单时，订单可创建。
- [ ] **支付宝配置缺失拒单**: 给定支付宝配置缺失，当提交合法支付宝订单时，请求被拒绝且不创建订单。
- [ ] **查询**: 给定授权管理员和一笔支付宝订单，当查询时，返回足以完成支付核对且渠道正确的信息。
- [ ] **未授权**: 给定未授权请求，当访问查询或人工重试时，访问被拒绝。
- [ ] **人工重试**: 给定已支付且通知失败的订单，当授权管理员重试时，复用原任务，通知最终成功，且审计包含操作者。
- [ ] **密钥隔离**: 给定运行中的服务，当检查配置来源和日志时，支付宝私钥与微信密钥分开存放，日志中无完整密钥。
- [ ] **仓库与镜像**: 给定代码仓库、镜像和数据库抽样，当检索时，找不到支付宝应用私钥明文。
- [ ] **告警**: 给定支付宝通知积压或人工审查，当观察指标时，可与微信渠道区分并触发配置的告警。

## 3. 范围说明

**范围内 (In Scope)**:
- 双渠道配置完整性、密钥隔离、查询与人工补偿授权、审计、按渠道可观测性、回滚时保留补偿能力

**范围外 (Out of Scope)**:
- 易支付字段校验与允许列表（见 `epay-alipay-intake.md`）
- 收银台展示（见 `alipay-scan-payment.md`）
- 验签核对与自动到账状态机（见 `alipay-settlement.md`）
- 完整可视化支付运营后台、自动退款
- 具体实现方案（由 `design.md` 承接）
