# Delta Spec: 按订单通知地址投递成功回调

> 本文件聚焦支付成功后向 new-api 发送易支付回调的目标选择，是对 `../proposal.md §2.3` 的精化。
> 它修订变更 #45 `payment-settlement.md` 中「向配置的单一通知地址投递」的约束，不改变验签、金额核对、幂等和成功判定（正文去空白后等于 `success`）。

## 1. 需求描述 (中文 EARS)

**主流程**:
- 当已支付订单需要通知 new-api 时，支付适配器应读取该订单保存的通知地址，并仅向该地址发送易支付成功回调。
- 当回调目标仍属于当前允许列表时，支付适配器应使用本地已核对订单数据生成签名并投递。
- 当 new-api 响应成功且正文去除空白后严格等于 `success` 时，支付适配器应将通知任务置为成功并停止重试。

**前置约束**:
- 若订单保存的通知地址已不在当前允许列表内，支付适配器应拒绝本次投递，不得改投允许列表中的其他地址。
- 若无法读取订单通知地址，支付适配器应将本次尝试记为失败并按既有重试处理。
- 微信通知验签、字段核对和支付状态迁移仍须在创建或执行通知任务之前完成。

**异常与边界**:
- 当钱包充值订单支付成功时，支付适配器应投递到该订单的钱包通知地址，不得投递到订阅通知地址。
- 当订阅购买订单支付成功时，支付适配器应投递到该订单的订阅通知地址，不得投递到钱包通知地址。
- 当 HTTP 客户端跟随重定向时，支付适配器应再次确认目标仍属于允许列表。
- 在升级前已产生、升级后仍待投递的任务下，支付适配器应从订单保存的通知地址继续投递，不得要求改写历史任务内容。
- 浏览器同步返回不得作为到账依据。

## 2. 验收标准

- [ ] **钱包投递**: 给定已支付的钱包订单，当 Worker 投递时，HTTP 目标等于该订单保存的钱包通知地址。
- [ ] **订阅投递**: 给定已支付的订阅订单，当 Worker 投递时，HTTP 目标等于该订单保存的订阅通知地址。
- [ ] **禁止串单**: 给定允许列表含两条地址，当任一类订单支付成功时，对端对应业务完成结算，另一业务订单表不受影响。
- [ ] **移出列表**: 给定订单地址已不在当前允许列表，当 Worker 处理任务时，不发起对该地址或其他列表地址的成功投递，任务进入重试或终止策略。
- [ ] **重定向约束**: 给定回调响应重定向到非允许列表地址，当客户端处理重定向时，投递失败。
- [ ] **历史任务**: 给定升级前已确认支付、通知未完成的订单，当升级后 Worker 恢复时，仍向订单保存地址投递。
- [ ] **成功判定不变**: 给定 new-api 返回前后带空白的 `success`，通知任务置为成功。

## 3. 范围说明

**范围内 (In Scope)**:
- 通知任务执行时的目标选择、允许列表二次校验、重定向目标校验。
- 升级兼容：不改通知任务载荷结构，从订单行读取目标。

**范围外 (Out of Scope)**:
- 进单允许列表与配置解析，由 `notify-url-allowlist.md` 负责。
- 微信通知验签、状态机、租约、退避间隔、人工重试入口。
- new-api 侧钱包充值与订阅完成逻辑。
- 具体实现方案（由 `design.md` 承接）。
