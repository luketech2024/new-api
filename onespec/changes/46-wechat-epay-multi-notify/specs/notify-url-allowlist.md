# Delta Spec: 通知地址允许列表与进单校验

> 本文件聚焦支付适配器对 new-api 异步通知地址的配置与进单校验，是对 `../proposal.md §2.1 / §2.2` 的精化。
> 它修订变更 #45 `epay-order-intake.md` 中「通知地址必须与单一配置精确相等」的约束，不改变签名、金额和商户身份规则。

## 1. 需求描述 (中文 EARS)

**主流程**:
- 当运维配置一条或多条完整 HTTPS 通知地址时，支付适配器应加载为允许列表并完成启动。
- 当 new-api 提交字段完整、签名有效且通知地址属于允许列表的订单时，支付适配器应创建订单，并保存该订单使用的规范化通知地址。
- 当配置只含一条合法通知地址时，支付适配器应仅接受该地址，行为与单一精确匹配等价。

**前置约束**:
- 若通知地址允许列表为空，或任一配置项不是合法 HTTPS 公网地址，支付适配器应拒绝启动。
- 若请求中的通知地址规范化后不属于允许列表，支付适配器应拒绝请求且不得创建订单。
- 若商户身份、支付类型、签名或金额不合法，支付适配器应仍按既有规则拒绝，不得因允许列表放宽这些校验。

**异常与边界**:
- 当允许列表同时包含钱包充值通知地址和订阅购买通知地址时，支付适配器应分别接受两类订单。
- 当允许列表仅包含其中一类地址时，支付适配器应拒绝另一类业务的进单。
- 若相同商户订单号以不同通知地址再次提交，支付适配器应拒绝冲突并保留原订单。
- 若相同商户订单号以相同关键字段（含通知地址）再次提交，支付适配器应返回原订单结果。
- 允许列表应做完整地址匹配；支付适配器不得仅因与某条允许地址同域或同路径前缀而放行。

## 2. 验收标准

- [ ] **双地址启动**: 给定两条合法完整通知地址，当适配器加载配置时，进程成功启动。
- [ ] **单地址兼容**: 给定一条合法完整通知地址，当适配器加载配置时，进程成功启动且仅该地址可进单。
- [ ] **配置非法**: 给定空列表或含非 HTTPS 项的配置，当适配器启动时，进程失败且不对外进单。
- [ ] **钱包进单**: 给定允许列表含钱包通知地址，当合法钱包充值请求到达时，适配器创建订单并保存该钱包通知地址。
- [ ] **订阅进单**: 给定允许列表含订阅通知地址，当合法订阅购买请求到达时，适配器创建订单并保存该订阅通知地址。
- [ ] **越权拒绝**: 给定允许列表不含某完整路径，当请求携带该路径时，适配器拒绝且不创建订单。
- [ ] **冲突拒绝**: 给定已存在订单，当相同订单号携带不同通知地址时，适配器拒绝、保留原订单并记录审计。

## 3. 范围说明

**范围内 (In Scope)**:
- 通知地址配置的多值解析、启动校验与规范化。
- 进单时对通知地址的允许列表匹配，以及把命中地址写入订单。
- 因通知地址不同导致的订单冲突检测。

**范围外 (Out of Scope)**:
- 支付成功后向 new-api 投递回调，由 `per-order-callback-delivery.md` 负责。
- 同步返回地址白名单策略本身（仍为 origin/路径前缀）；仅要求运维配置覆盖订阅回跳。
- 微信 Native 下单、收银台、验签与状态机。
- 具体实现方案（由 `design.md` 承接）。
