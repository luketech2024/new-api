# 变更提案: 微信支付适配器同时支持钱包充值与订阅回调

## 1. 需求背景 (工作项来源)
> 处理人: lukezhang
> 优先级: P0

以下内容由本地已落地实现对照 PRD 整理，无禅道 Story ID。需求文档见 `onespec/prd/wechat-epay-multi-notify/prd.md`。

变更 #45 建设了独立微信支付适配器，首期以钱包充值为验收主场景，并把 new-api 异步通知地址做成全局唯一精确值。new-api 钱包充值与订阅购买各自拼接不同的异步回调路径，后台「回调地址」只填站点根域名。结果是适配器环境里只能写一条完整通知地址，两条业务无法同时走通。

本变更只改适配器模块：通知地址改为允许列表，进单按列表校验，成功后按订单保存的地址投递。不修改 new-api 源码及其两个回调接口。

## 2. 变更详情

### 2.1 通知地址允许列表
**配置与兼容**
- **现状**：适配器启动时要求一条精确的 new-api 通知地址；进单和投递都绑定这一条。
- **目标**：当运维配置一条或多条完整 HTTPS 通知地址时，支付适配器应成功启动；当配置为空或含非法地址时，支付适配器应拒绝启动。当配置只含一条合法地址时，支付适配器应保持与改前等价的单地址行为。
- **原因**：new-api 为不同业务登记不同回调路径，但共享同一易支付网关与同一适配器实例。
- **影响**：环境变量键名不变，取值从单地址变为逗号分隔列表；需更新部署示例。new-api 后台回调字段语义不变。

### 2.2 进单按允许列表校验并保存订单通知地址
**Epay 订单接入**
- **现状**：进单要求请求中的通知地址与全局配置精确相等，否则拒绝且不创建订单。
- **目标**：当请求通知地址属于允许列表时，支付适配器应创建订单并保存该订单使用的规范化通知地址；当请求通知地址不在允许列表内时，支付适配器应拒绝请求且不得创建订单。当相同商户订单号携带不同通知地址再次提交时，支付适配器应拒绝冲突。
- **原因**：订阅购买与钱包充值会带上不同通知路径，必须在入口同时放行，又不能放开任意同域路径。
- **影响**：进单校验从「等于唯一配置值」变为「命中允许列表」；请求摘要继续包含通知地址，冲突检测保持有效。

### 2.3 成功回调按订单地址投递
**下游通知**
- **现状**：通知 Worker 始终向全局配置的那一条地址投递，忽略订单上已保存的通知地址。
- **目标**：当订单已支付需要通知 new-api 时，支付适配器应向该订单保存的通知地址发送易支付成功回调。若该地址已不在当前允许列表内，支付适配器应拒绝投递并按既有失败重试处理，不得改投列表中的其他地址。
- **原因**：错误投递会导致对端查不到订单并返回失败，或误入另一业务结算逻辑。
- **影响**：投递目标从进程常量改为订单字段；HTTP 客户端的目标校验需与允许列表对齐。通知任务快照无需迁移。

### 2.4 明确不做
- 不修改 new-api 钱包或订阅的回调处理、订单号规则、后台「回调地址」字段。
- 不把两条业务回调合并为单一入口，也不按订单号前缀在适配器内调用不同结算逻辑。
- 不改变微信 Native 下单、收银台、验签解密、支付状态机、人工补偿和金额精度规则。
- 不实现运行时热更新允许列表。

### 2.5 风险与应对
- 风险点: 允许列表配漏导致一侧业务进单失败；投递改用订单字段后出现 SSRF；升级后历史待投递任务目标错误；同步返回白名单过窄导致订阅回跳被拒。
- 应对措施: 允许列表使用完整 URL 精确匹配而非路径前缀；投递前与 HTTP 传输层均再校验允许列表；历史任务从订单行读取已保存地址；部署说明同时覆盖通知地址与同步返回允许范围。
- 回滚策略: 将环境变量恢复为单条钱包或单条订阅地址并重启适配器；已支付未通知订单保留人工补偿；不得删除支付订单或撤销已确认到账。
